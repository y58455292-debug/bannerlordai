BANNERLORDAI — DURABLE HANDOFF / CONTINUITY PRIOR ART
Date: 2026-09-18 Pacific

Question:
Can a cross-chat engineering handoff be designed so a replacement agent resumes from durable state rather than reconstructing work from a summary?

Finding:
YES. Multiple mature architectures independently use the same underlying mechanisms.

1. TEMPORAL DURABLE EXECUTION
Source: https://docs.temporal.io/
Official documentation describes crash-proof workflows that resume after process/infrastructure failure.
Transferable mechanism:
- durable workflow history
- resume after interruption
- execution state independent of one worker/process lifetime

2. LANGGRAPH PERSISTENCE / CHECKPOINTING
Sources:
https://langchain-ai.github.io/langgraphjs/how-tos/cross-thread-persistence-functional/
https://langchain-ai.github.io/langgraph/reference/checkpoints/
https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph
Transferable mechanism:
- checkpoint thread state
- separate thread-scoped checkpoints from cross-thread durable stores
- preserve completed writes across failure
- resume at explicit execution boundaries
- smaller execution nodes create more frequent safe recovery points
3. EVENT SOURCING + SNAPSHOTS
Source:
https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing
Transferable mechanism:
- append-only immutable event history as system of record
- reconstruct current state by replay
- snapshots reduce replay cost but do not replace the event history
- sequence/order and optimistic concurrency matter
- events should capture intent, not merely resulting values

4. SINGLE-ACTIVE OWNER / LEASE
Sources:
https://kubernetes.io/docs/concepts/architecture/leases/
https://kubernetes.io/docs/concepts/cluster-administration/coordinated-leader-election/
Transferable mechanism:
- one active owner performs control work
- ownership identity + acquire/renew times + duration
- followers do not perform conflicting writes
- expired ownership can be safely taken over
- optimistic concurrency prevents two owners from acquiring simultaneously

BannerlordAI adaptation:
- append-only Handoff event journal is the durable history
- current.json is a materialized resume snapshot, not the only truth
- immutable periodic snapshots bound replay time
- every live deployment/test has a stable operation ID and PREPARED/ACTIVE/COMPLETED phase
- repeated operation IDs are idempotent: next agent inspects/resumes instead of repeating
- deployment/runtime ownership uses one-owner lease semantics
- Mem stores durable roadmap/architecture rules; local journal/checkpoints store exact volatile work state
- runtime/process/hash inspection remains authoritative for external side effects
Adoption gate:
This architecture is accepted because the core mechanisms are established independently in durable workflow systems, agent checkpointing systems, event-sourced systems, and high-availability controllers.
We are adapting the mechanisms, not importing a framework blindly.

Limitations:
- Chat model internal hidden reasoning cannot be serialized/replayed; continuity is achieved by persisting explicit project state, decisions, evidence, operations, and next work.
- External side effects must be idempotent or inspected before retry.
- Event logs need schema/version discipline and integrity checks.
- Snapshot data is an optimization/materialized view; immutable evidence remains authoritative.
- Lease ownership must never be stolen merely because another chat exists; expiry/process evidence must be checked.

Standing rule:
For future workflow/rule/architecture changes requested by the user:
SEARCH RELIABLE PRIOR ART FIRST.
If no credible mechanism/evidence exists, do not promote the idea into project doctrine.
If credible architecture exists, map the mechanism to BannerlordAI, state limitations, make the smallest safe adaptation, validate it, then preserve it in Handoff + Mem.
