BannerlordAI v0.2.10.53 - Retry-attempt rotation / stale-result rejection integration shadow

Question
After transient failure and explicit release/reclaim, does the system reject a stale result from the old attempt and accept only the currently claimed retry attempt?

Why this gate
- v0.2.10.52 proves explicit release/reclaim mechanics.
- v0.2.10.51 proves result envelopes must match the active claim.
- The important concurrency composition still needs end-to-end proof across an actual retry rotation.

Implementation
- Reuse v0.2.10.52 ClanAI/runner binaries unchanged.
- Validator-only integration flow:
  1. Natural route-eligible request enqueues one job.
  2. Claim providerId=deterministic_external_worker, attemptId=attempt-1.
  3. Submit TRANSIENT_FAILURE result for attempt-1 -> CLAIM_MATCHED, retryable, queue retained.
  4. Explicit release attempt-1 -> CLAIMED -> PENDING.
  5. Claim attempt-2 -> PENDING -> CLAIMED.
  6. Submit stale SUCCESS result for attempt-1:
     must reject PROVIDER_CLAIM_MISMATCH,
     must not consume pending advisory request,
     must not remove queue job.
  7. Submit exact SUCCESS result for attempt-2:
     must CLAIM_MATCHED,
     nested KEEP_BASELINE advisory admitted,
     SUCCESS_ACKED removes queue 1 -> 0.
  8. Replay attempt-2 result must fail DISPATCH_JOB_NOT_FOUND / queue 0 -> 0.
- Provider invocation stream remains empty.
- No real network/model call.

Acceptance
A. Feature binaries exactly reused from v0.2.10.52.
B. Existing 173 fixtures remain PASS.
C. Live stale attempt-1 SUCCESS after attempt-2 claim:
   providerResultAccepted=false,
   claimMatchReason=PROVIDER_CLAIM_MISMATCH,
   pending advisory request remains available,
   completion retains queue 1 -> 1.
D. Live exact attempt-2 SUCCESS:
   CLAIM_MATCHED,
   providerResultAccepted=true,
   nested KEEP_BASELINE admitted,
   SUCCESS_ACKED queue 1 -> 0.
E. Replay attempt-2:
   DISPATCH_JOB_NOT_FOUND,
   queue 0 -> 0.
F. No provider invocation/network/model/Apply authority; full EXIT_NOSAVE cleanup.

Scope
Integration-only proof of retry ownership rotation and stale-result rejection. No new product behavior, timeout, retry-count, backoff, or real provider/model connection.
