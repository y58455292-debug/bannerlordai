BANNERLORDAI — DEPLOYMENT OWNERSHIP LEASE UPGRADE DESIGN
Date: 2026-09-18 Pacific
Status: DESIGN ACCEPTED FROM PRIOR ART; DO NOT MODIFY ACTIVE OWNER LOCK UNTIL CURRENT OWNER RELEASES.

Observed problem:
The installed ClanAI DLL changed while DEPLOYMENT_OWNER.json still identified a different expected build owner.
A static lock file is therefore insufficient as the final concurrency mechanism if writers bypass or outlive it.

Reliable prior art:
Kubernetes Lease / coordinated leader election.
Official mechanism:
- holder identity
- acquire time
- renew time
- lease duration
- lease transition counter
- only one active leader performs controller work
- optimistic concurrency/resource version prevents simultaneous acquisition
- expired leadership can be taken over only after timeout/evidence

BannerlordAI adaptation proposal:
deployment_lease.json fields:
- schema/version
- lease_revision (monotonic)
- holder_id
- chat/workflow operation_id
- milestone
- expected_installed_hash
- acquired_at
- renewed_at
- lease_duration_seconds
- process/run identifiers
- phase PREPARED/DEPLOYED/ACTIVE/EVIDENCE_FROZEN/COMPLETED/ABORTED
- transition_count

Rules:
1. Acquire with compare-and-swap against lease_revision.
2. Renew while controlling deployment/runtime.
3. Every deployment/launch script verifies holder_id + revision + expected installed hash immediately before external mutation.
4. Any mismatch aborts before writing/launching.
5. A different agent may take over only after lease expiry AND runtime/process inspection proves the previous operation is no longer active.
6. Completion releases/ends lease only after evidence freeze, process closeout, installed hash and save-integrity checks.
7. Never steal a lease merely because another chat is open.
8. Research/build can remain parallel; live deployment/runtime stays single-owner.

Adoption condition:
Wait until the current DEPLOYMENT_OWNER.json holder releases or is conclusively stale. Build/test the lease mechanism offline first, then migrate.
