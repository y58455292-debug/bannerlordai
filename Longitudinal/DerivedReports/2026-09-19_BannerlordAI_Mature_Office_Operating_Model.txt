BannerlordAI Mature Office Operating Model — Research-backed design
Date: 2026-09-19
Status: DESIGN FOR IMPLEMENTATION / LAUNCH

PURPOSE
Reduce context switching, repeated reasoning, duplicate work, and chat saturation while preserving correctness, evidence quality, safe live control, and rapid project progress.

RESEARCH BASE
1. FEMA Incident Command System / NIMS
   - Clear chain of command, unity of command, modular organization, manageable span of control, transfer of command, management by objectives.
   - Adaptation: each work item has one accountable owner; live Bannerlord control remains single-owner; emergency/debug authority may transfer explicitly.

2. Team Topologies (Skelton & Pais, 2019/2025)
   - Team cognitive load, fast flow, clear team interaction modes, evolving structures.
   - Adaptation: Front, Coder, Analyzer, Supervisor have sharply bounded responsibilities; routine interactions become service-like; novel architecture uses temporary collaboration.

3. Google SRE / SRE Workbook
   - Eliminate repetitive toil; automate recurring operational work; structured incident roles; blameless postmortems; keep working records; clear operational communication.
   - Adaptation: repeated task -> guard/automation; major failure -> mini-postmortem; raw logs stay local; chat publishes only meaningful milestones/blockers.

4. DORA
   - Smaller change batches improve speed, rationality, recovery and stability; teams should identify and improve the most significant constraint.
   - Adaptation: one hypothesis -> one intervention -> one measurable result; avoid giant multi-feature live tests.

5. Kanban Method
   - Limit work in progress; pull work based on capacity; WIP overload harms flow, predictability and quality.
   - Adaptation: Coder WIP=1 active live action; Analyzer WIP=1 reasoning review; one primary roadmap objective at Front Office.

6. Theory of Constraints / The Goal
   - Overall flow is governed by the active constraint/bottleneck.
   - Adaptation: Daily Plan explicitly names the current bottleneck; other desks support it instead of starting unrelated parallel work.

7. High Reliability Organization research (AHRQ)
   - Preoccupation with failure, reluctance to simplify, sensitivity to operations, commitment to resilience, deference to expertise.
   - Adaptation: near misses are valuable; runtime evidence outranks status assumptions; Coder evidence can overrule Front assumptions; Analyzer examines alternate explanations before promotion.

8. Microsoft/ACM developer productivity research
   - Developers report greater productivity with fewer interruptions/context switches; task switching and interruptions impose recovery cost.
   - Adaptation: department chats suppress routine chatter; Front absorbs user-facing interruptions; Coder gets protected execution blocks; Analyzer does not interrupt active live runs for noncritical review.

ORGANIZATION
FRONT OFFICE / COORDINATOR
- One primary user-facing hub.
- Maintains logical chat directory, roadmap priority, daily plan, office status, and major update stream.
- Does not debug code in the hot path.
- May change priorities but cannot bypass safety/ownership/integrity gates.
- During major incident: serves as Incident Commander + Communications Lead unless explicitly transferred.

CODER / OPERATOR
- Stream-aligned delivery desk for implementation and live execution.
- Owns code, builds, validator runs, logs, raw errors, reproducible evidence.
- One active live work item at a time.
- Produces Coder Desk result -> Analyzer intake.
- During major incident: serves as Operations Lead / technical responder.

ANALYZER / ARCHIVIST
- Enabling/review desk.
- Read-only with respect to live Bannerlord control.
- Reviews Coder evidence; separates observation from inference.
- Maintains knowledge system: FRONT/HOT/WARM/RAW pyramid, policies, architecture lessons, do-not-repeat rules, efficiency cheatsheets, references, acceptance criteria.
- During major incident: serves as Scribe / Evidence / Postmortem Lead.

SUPERVISOR / PLATFORM
- Platform-like deterministic service.
- Always-on continuity, clock enforcement, WIP/ownership enforcement, registered action dispatch, duplicate prevention, integrity checks.
- Executes no novel reasoning.
- Can refuse dispatch; cannot invent new work.

WORK INTERACTION MODES
1. SERVICE MODE (default)
   Front -> approved objective; Supervisor -> registered work; Coder -> evidence; Analyzer -> review; Front -> user update.
2. COLLABORATION MODE (temporary)
   Used only for genuinely new architecture / ambiguous blocker. Front + Coder + Analyzer share context until a new deterministic rule can be encoded.
3. FACILITATING MODE
   Analyzer helps Coder with evidence/prior art/process improvement without owning live execution.

WIP LIMITS
- One primary roadmap objective.
- Coder: max 1 active live/runtime task; max 1 offline preparation task.
- Analyzer: max 1 reasoning-heavy review; indexing can be automatic.
- Supervisor: one dispatched action at a time.
- Front: max 2 queued priority changes before re-plan.
- New work is PULL-based: a desk pulls the next item only when capacity is free.

WORK CLASSES
- LIVE_GAME: launches/controls Bannerlord. OPEN hours only. Requires lease, protected-save gate, registered action.
- DEPLOYMENT: changes installed test artifacts. OPEN hours only. Requires lease.
- VALIDATOR: deterministic proof harness. OPEN hours if it may launch game; otherwise OFFLINE.
- OFFLINE_CODE: edits/staging with no live runtime side effects. Allowed during OPEN + AFTER_HOURS.
- BUILD: compile/hash/static build. Allowed during OPEN + AFTER_HOURS.
- STATIC_ANALYSIS: reflection/search/read-only inspection. Allowed during OPEN + AFTER_HOURS.
- EVIDENCE_REVIEW: Analyzer read-only review. Always allowed.
- RESEARCH: Analyzer/Front reliable prior-art study. Always allowed, no live control.
- MAINTENANCE: index rebuild, continuity, metrics. Supervisor always allowed.
- INCIDENT: temporary emergency mode; freezes normal backlog.

OFFICE MODES / CLOCK
OPEN (default configured 07:00-23:00 Pacific)
- Full office.
- Coder allowed LIVE_GAME / DEPLOYMENT / VALIDATOR.
- Analyzer active as needed.
- Supervisor always active.
- Front available.

AFTER_HOURS (23:00-07:00 Pacific)
- No new live Bannerlord runs or deployments.
- Coder may perform OFFLINE_CODE / BUILD / STATIC_ANALYSIS only.
- Analyzer may continue read-only review/research/indexing.
- Supervisor maintains continuity/integrity.
- Front remains available.
- User may explicitly override hours for a specific work class/period.

CLOSED / MAINTENANCE
- No Coder work.
- Supervisor continuity + Front status only unless user explicitly overrides.
- Analyzer optional read-only if Front assigns.

DAILY PLANNING
Front Office generates one Daily Plan from:
- accepted milestone,
- active candidate/question,
- blockers,
- Analyzer intake,
- registered deterministic queue,
- office clock,
- current bottleneck.

Daily Plan assigns each desk:
CLOCKED_IN / ON_CALL / STANDBY / CLOCKED_OUT
plus:
- objective,
- allowed work classes,
- WIP limit,
- completion condition,
- escalation condition,
- next handoff.

CHAT HYGIENE
Department chats are LOG SURFACES, not raw terminals.
Publish only:
- accepted/rejected major milestone,
- meaningful task completion,
- genuine blocker/integrity drift,
- material debugging breakthrough,
- architecture/policy change,
- daily plan/closeout when requested.

Suppress:
- routine passing checks,
- raw compiler output,
- ordinary polling,
- repeated command acknowledgments,
- duplicate explanations already stored on disk.

CHAT ROLE ACTIVATION
- "Front office" -> whole-office status / coordination.
- "Coder desk" -> implementation/runtime worker role.
- "Analyzer desk" -> evidence/review/knowledge role.
- "Supervisor desk" -> schedule/integrity role.
New chat must recover from disk first; chat transcript is never operational authority.

INFORMATION PYRAMID
FRONT: immediate operational summary.
HOT: current verified technical state.
WARM: indexed summaries/policies/research blocks.
RAW: logs/source/validators/history.
Agents descend only as far as the question requires.

INCIDENT MODE
Trigger:
- protected save drift,
- ownership conflict,
- unexpected live process,
- rollback failure,
- repeated failure not reducing uncertainty,
- unknown side effect.

Incident roles:
- Front = Incident Commander / Comms.
- Coder = Ops Lead.
- Analyzer = Scribe / Evidence / Postmortem.
- Supervisor = interlocks / runtime guard.
Normal roadmap work freezes until contained.

POSTMORTEM-LITE REQUIRED WHEN
- protected/integrity gate is violated or nearly violated,
- same failure repeats twice,
- manual recovery was needed,
- a harness false negative wastes a full live run,
- unexpected behavior changes test interpretation.

Postmortem fields:
what happened / impact / evidence / contributing conditions / classification / fix / automation or guard added / do-not-repeat rule / follow-up acceptance test.

FLOW / BOTTLENECK POLICY
- Daily Plan names one active bottleneck.
- Protect bottleneck from noncritical interruptions.
- Other desks support bottleneck instead of creating parallel WIP.
- Re-plan whenever bottleneck changes.

TOIL POLICY
- Repeated manual/repetitive/automatable work is tracked as toil.
- Second recurrence -> automation candidate.
- Third recurrence -> automation/guard required unless human judgment is essential.
- Front/Analyzer periodically review toil sources.

QUALITY / PERFORMANCE METRICS
- Accepted milestone lead time.
- Registered action success/failure rate.
- Harness false-negative rate.
- Duplicate-run preventions.
- Fast-resume time vs deep-resume time.
- Analyzer review latency.
- Coder WIP age.
- Protected-save integrity rate.
- Repeated-failure count.
- Toil converted to automation.
- Chat update signal/noise (material updates vs routine messages).

LAUNCH CRITERIA
Office may launch only when:
- department directory exists,
- clock enforcement is active,
- daily plan generator works,
- Supervisor enforces work class + office mode,
- Coder -> Analyzer automatic handoff works,
- Front Office snapshot includes departments/clock/plan,
- chat publishing policy is durable,
- automations follow department schedules,
- test run proves no duplicate dispatch and correct clock refusal.
